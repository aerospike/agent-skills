Mitigated by naming the repository in the generated header so a cited filename resolves once the repo is public. | Closed |

The floor is 7.0 because `cluster-name` became mandatory in Database 7.0.0, so the documented local flow cannot work below it. `tests/unit/test_skill_metadata.py` locks it in, and also guards its own parametrize list so a new skill folder cannot slip past uncovered. | Closed |
| F7 | `aerospike-data-modeling` has never been measured: absent from the evaluation harness `source_skills` and from all 61 tasks. | **Fix in flight.** Seven tasks added in [`tasks/data-modeling.yaml`](tasks/data-modeling.yaml). A mock run covered 68 tasks (61 + 7) across 6 variants with all four pipeline stages green. Stays open: a mock run measures plumbing, not accuracy. Closing needs that pull request merged and a live run reporting numbers. (The harness remote is under `citrusleaf`, not `aerospike`.) | Open — awaiting harness merge and a live run |
| F8 | Skill folders are self-contained; no relative link escapes its own folder. | **Fixed (locked in).** [`unit/test_payload_integrity.py`](unit/test_payload_integrity.py) asserts it for all four skill folders, and additionally asserts that every relative link resolves to a file that exists — eight checks, two per folder. The second check was not the regression guard it was expected to be: it failed on its first run and found a real defect, recorded as F15. | Closed |
| F9 | `dev-ttl-void-time` failed on every variant including the baseline in evaluation run `20260623-101343`, attributed to the task rubric rather than a skill defect. | **Fixed, and the suspicion confirmed.** A grader defect, not a skill defect. The task's second `forbidden` pattern, `flip[^.]{0,30}never-?expire[^.]{0,30}(short\|finite\|ttl)`, matched the exact vocabulary the prompt itself invites, so an answer that correctly warned against the user's plan was failed for echoing the question. Verified by grading a realistic correct warning through the harness's own `grade_output`: `correctness` 0.0 before the fix, 1.0 after, while genuine endorsements still fail. Replaced with a pattern that fires only on endorsement, in the same pull request as F7. | Closed |
| F10 | The compiled skill cites two GitHub URLs that return HTTP 404 to a link checker: `https://github.com/aerospike/agent-skills` in the generated header, and `https://github.com/aerospike/data-modeling-guide` in a data-modeling rule. Neither repository is public yet. | **Narrowed.** Full link checking stays on `skills/`. `validate-skill.sh` skips the `links` group for `compiled-skills/` only: those links are inherited from `skills/` (already checked), and leaving the compiled root failing would keep the CI gate red on every PR. Verifying both URLs resolve is a manual pre-publish step (see [tests/README.md](README.md#before-publishing)). | Closed |
| F11 | `skill-validator` warns that the published description reads as a keyword list (13 comma-separated segments). | **Accepted.** The description is the only input to whether an agent loads the skill, so breadth of matchable phrasing is the point. | Closed |
| F12 | `skill-validator` warns the published body is 9,163 tokens against a recommended 5,000. | **Accepted.** Measured, not incidental: the evaluation sized the stripped digest at roughly 8.5k tokens and found it as accurate as the full monolith. | Closed |
| F13 | `skills-ref` requires Python 3.11 or newer, but the repository's other tooling runs on the system Python, which is 3.10 here. | **Fixed.** Contributor setup names `python3.11` explicitly when creating the validator virtualenv. | Closed |
| F14 | The published description under-reached design-time data modeling. First measured run against `composer-2.5` scored accuracy 0.920, precision 1.000, recall 0.833 over the 25-case corpus; both failures were data-modeling positives (`pos-dm-key-design`, `pos-dm-schema-review`) and nothing over-fired. | **Fixed.** The description in `scripts/skills_compile/published_skill.yaml` was widened where it was narrow: "design a data model from requirements" became "design or review a data model, whether from requirements or against a schema that already exists", and the Use-when clause gained "chooses keys or models data for it, reviews an Aerospike schema before building". Two further runs scored 0.960 and 0.920, precision 1.000 both times, and the two target cases passed three times out of four. The failures move between runs — run 2 failed `pos-dev-policy-timeouts`, run 3 failed `pos-dev-cdt-map-update` and `pos-dm-schema-review` — so routing is stochastic and a threshold of 1.0 would fail on noise. CI gates at 0.88, the worst run minus one case; all three runs and the margin's reasoning are tabulated in [`triggers/README.md`](triggers/README.md). | Closed |
| F15 | `skills/aerospike-development/references/_template.md` carried a dead relative link to a nonexistent `other-rule.md`. The template is authoring scaffolding, excluded from compilation by `_SKIP_REFS`, so the dead link never reached the published payload — but every rule authored from the template inherited it. | **Fixed.** The placeholder was rewritten so the `[...]` and `(...)` are separate code spans and no longer parse as a Markdown link. Found by F8's link-resolution check on its first run, which is the check earning its keep before it ever became a regression guard. | Closed |
| F16 | Whether the getting-started skill's claims still hold against a current server had never been executed, only read. | **No drift found.** [`content/verify-server-claims.sh`](content/verify-server-claims.sh) booted `aerospike/aerospike-server:latest` and verified all 8 claims against build **8.1.2.4-4**, 0 failed: the Community image boots and serves, the build is 7.0 or newer, namespace `test` exists and `default` does not, `cluster-name` is a service config key, `nsup-period` and `default-ttl` are namespace config keys, and client port 3000 is reachable from the host. A clean run is the result, not the absence of one. | Closed |
| F17 | Two ways `verify-server-claims.sh` can report failure that is not drift. It binds host ports 3000-3002, so it collides with an Aerospike already running locally. And not every published image tag ships `asinfo` — tag `8.1.3.0-76-g06cc9dd7f-amd64` has none — so `--tag` against such a build reports eight simultaneous FAILs that look like drift but are a tooling gap. | **Documented, not fixed.** Both are recorded in [`README.md`](README.md) rather than worked around: the port binding is deliberate (the claim being checked is that port 3000 is reachable *from the host*), and eight simultaneous failures are a recognisable signature of a missing `asinfo` rather than of drift, which spot-drifts one claim at a time. Revisit if either causes a real misread. | Open — accepted, with the signature documented |
| F18 | Grounding the new data-modeling task corpus against the harness's real grader found that 4 of the plan's proposed `forbidden` patterns would have hard-failed correct answers, and 2 `required_all` patterns were vacuous — bare `SI` matches "de-SI-gn", bare `cap` matches "capacity". | **Fixed before commit.** The patterns were corrected in `tests/tasks/data-modeling.yaml`. The wider point is that the F9 class of defect is systemic in regex-graded rubrics, not a one-off: a pattern meant to catch a wrong answer catches the right one whenever the prompt supplies the vocabulary. Every new rubric pattern should be run against a realistic correct answer, not only a wrong one. | Closed |
| F19 | The harness reads task prompts through its `vendor/agent-skills` submodule. If the pointer is left at its old commit, `glob` on the then-missing `tests/tasks/` returns empty silently, so a run scores the stale 61-task corpus while appearing healthy. | **Known risk, documented.** No exception is raised and no count is asserted, so the only signal is `n_tasks`. The harness pull request's README change says the pointer must be refreshed when prompts change, and `n_tasks` should be checked against the expected total on every run. A hard assertion belongs in the harness, not here. | Open — mitigation is in the harness repository |
| F20 | Client API signatures in the skills had never been checked against current SDK documentation; the design left this as a manual pass because automating it is not worth the cost. | **Pass done 2026-08-19** against Python client 19.2.2, Node.js client 6.7.1, Go client v8.8.0, Java client 10.4.0. Verified correct: the Python factory `aerospike.client(config)` and the claim that `.connect()` is a no-op on a fresh client (constructor connects as of Python client 8.0.0); `put(key, bins[, meta[, policy]])`, `get(key[, policy]) -> (key, meta, bins)`, `operate(key, list[, meta[, policy]]) -> (key, meta, bins)`, `batch_read(keys[, bins][, policy]) -> BatchRecords` with results at `.batch_records`; `list_operations.list_insert(bin_name, index, value, policy)`, `KeyOrderedDict`, `POLICY_KEY_SEND`; the Node.js `Aerospike.connect(config)`, `new Aerospike.Key(ns, set, key)`, `put(key, bins, meta, policy)`, `get(key, policy)`, `WritePolicy`/`ReadPolicy` with `totalTimeout`, and `maxConnsPerNode`; the Go `v8` import path; the Java `aerospike-client-jdk21` / `aerospike-client-jdk8` artifact split. **Two drifts found**, both in authoring sources only — neither reaches the published payload, because the stripped renderer does not carry `ex-` code blocks: `references/ex-policy-explicit-defaults.md` sets `policies: {"timeout": 1000}`, a client config key removed in Python client 3.0.0 in favour of `total_timeout` inside each policy dict (silently ignored today, since `validate_keys` defaults to false, and a `ParamError` if it is set); and `references/ex-batch-read-by-keys.md` shows `client.batch_get(policy, keys)`, a method the Python client has never had — the nearest, `get_many`, was deprecated in 12.0.0 and removed in 17.0.0 — with an argument order no Python batch API uses. **Both fixed.** `total_timeout` replaces `timeout`; the conceptual batch sketch no longer names a method, and points at [`ex-official-batch.md`](../skills/aerospike-development/references/ex-official-batch.md), whose Python snippet already showed the correct `client.batch_read(keys)` — the two files had been contradicting each other. | Closed |
| F21 | The trigger-accuracy workflow could not gate anything: `CURSOR_API_KEY` is not configured on the repository, and the job-level `if` only excluded forks, so same-repo pull requests failed on the missing credential rather than on anything about the skill. | **Removed from CI.** This project does not put a model API key in its CI, so trigger accuracy is a manual pre-publish check instead, documented in [tests/README.md](README.md#before-publishing) and [tests/triggers/README.md](triggers/README.md). The runner separates scoring from the model calls, so the corpus, verdict parsing, and scoring stay covered by unit tests with no key and no network — only the measurement is manual. `test_ci_workflows.py` asserts no workflow reaches for the key, so the decision cannot erode back into a permanently-skipping gate. | Closed |
| F22 | The `skill-validator` job's summary step called `skill-validator check ... skills/ compiled-skills/`, but the command accepts exactly one path and rejected it with `accepts 1 arg(s), received 2`. The step had restated policy — the root list, and the `--skip links` that applies only to `compiled-skills/` — that `scripts/validate-skill.sh` already owned. Introduced in workstream A; the job was red on every pull request. | **Fixed.** `validate-skill.sh` gained a `--summary` mode and the workflow calls it, so the roots and the skip policy exist in one place. `test_ci_workflows.py` fails if a workflow invokes `skill-validator check` directly again. | Closed |
